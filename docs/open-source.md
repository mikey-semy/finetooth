# Открыть finetooth как open-source проект: что нужно и кто рядом

Разбор 24.09.2026 по вопросу автора метода «а ты не можешь просто оформить его как
open-source проект на GitHub?». Чек-лист собран по пути, который владелец уже прошёл с
первым проектом (там — «открытые края при закрытом центре», пять слоёв, предполётная
проверка репозиториев), плюс то, что у этого набора особенное. Каталог соседей — по
GitHub API на 24.09.2026: звёзды и даты пуша сняты запросом, а не из блогов.

## 1. Что у этого репозитория особенное

Три вещи, которых у первого проекта не было.

**Лицензия на основу.** Набор вырос из архива автора метода, переданного без лицензии;
наш `LICENSE` — MIT с приложением «основа передана без лицензии», и GitHub из-за
приложения показывает лицензию как **Other**. Для открытого проекта это первое, что
увидит посетитель, и это плохой знак. Автор сам предложил открыть проект — значит, нужно
его явное согласие на лицензию: одна строка от него (сообщение, коммит с `Signed-off-by`
или комментарий в issue), после чего `LICENSE` становится чистым MIT с двумя
правообладателями, а история происхождения уезжает в `NOTICE.md`.

**Автор под ограничениями GitHub.** По действующей политике GitHub для Крыма доступны
публичные репозитории, gists и бесплатные минуты Actions «для личного, некоммерческого
использования»; приватные репозитории и платные услуги — нет. Значит: в публичном проекте
автор участвует со своего аккаунта (issues, PR, `Co-authored-by`); в приватном — не мог,
что и было. Запасная площадка, если понадобится: GitLab.com (политику по регионам с сайта
вытащить не удалось — проверить руками), свой сервер. Codeberg под вопросом: условия
требуют свободной лицензии (после чистки LICENSE — ок) и **запрещают проекты, состоящие в
основном из кода, сгенерированного ИИ**, — `review.py` по истории коммитов ровно такой.

**Имя.** До 0.6.0 набор назывался `review-kit`, и соседей с похожими именами было много:
`draft-review-kit` (87★, ревью текстов), `ReviewKit` (Swift, два проекта),
`tender-review-kit`, `spec-kit-review` — по имени не найти. 24.09 выбран корень серии
**finetooth** (от идиомы *go through with a fine-tooth comb* — прочесать частым гребнем):
свободен на npm и PyPI, на GitHub — три крошечных репозитория; организация с таким именем
занята, под серию подойдёт `finetooth-review`. Отвергнуты: `review-combine` (авторское
слово «комбайн», но по-английски прежде всего глагол и десятки `review-*` рядом),
`codecensus` (точно про полное издание, но не тянет серию); `dragnet`, `blockwise`,
`muster` заняты на npm и PyPI. Серия по типам ревью: `finetooth` (сплошное по блокам),
`-lens` (по свойству), `-slice` (по сценарию), `-pr` (по изменению — лёгкая версия, бот
или Action), `-scan` (разведка по осям), `-shape` (по устройству: крупные файлы, горячие
точки, связанность), `-threat` (модель угроз), `-gate` (ворота в CI). Один репозиторий,
скиллы в `skills/`, каждый ставится отдельно.

## 2. Чек-лист открытия

**Решения владельца (до всего остального):**

1. Лицензия — MIT с двумя правообладателями; согласие автора получено и сохранено.
2. Имя репозитория — решено: `finetooth` (см. раздел 1).
3. Язык. Набор целиком на русском — это осознанно (промпты и отчёты читают русскоязычные
   агенты и люди). Для открытого проекта нужен хотя бы английский первый экран README и
   английское `description` в `SKILL.md` (там уже стоят английские ключевые слова для
   срабатывания скилла). Переводить всё — отдельное решение, не условие открытия.
4. Модель вклада — DCO (`Signed-off-by`), не CLA: у нас нечего защищать двойной
   лицензией, а CLA отпугивает.
5. Строка про поддержку — честная: «проект ведёт один человек, PR разбираются раз в
   неделю». Отсутствие обещаний лучше нарушенных.

**Предполётная проверка — сделана 24.09, результаты:**

| Проверка | Итог |
|---|---|
| имена людей и проектов в файлах | не найдено ни одного (после чистки под 0.1.0) |
| то же в истории коммитов | 0 совпадений по всей истории |
| ключи и адреса серверов | нет; в репозитории нет ни `.env`, ни инфраструктуры |
| авторы коммитов | два адреса владельца — ок |
| прогнать `gitleaks detect` по истории перед открытием | ещё нет |

**Обвязка репозитория (чего не хватает — по сверке с лучшими соседями, раздел 4):**

- [ ] `LICENSE` чистый MIT, `NOTICE.md` с происхождением;
- [ ] `CONTRIBUTING.md`: DCO, как гонять тесты и `skills-ref validate`, правило «каждая
      проверка — с мутацией» (оно уже в `AGENTS.md`), латиница в именах файлов;
- [ ] `CODE_OF_CONDUCT.md` — Contributor Covenant 2.1, без самодеятельности;
- [ ] `SECURITY.md`: куда писать и срок ответа «до недели»;
- [ ] шаблоны issue в `.github/ISSUE_TEMPLATE/*.yml` с `config.yml`; отдельный шаблон
      «нашёл дефект набором» (у Trail of Bits — `trophy-case.yml`: ссылка на находку и
      какой скилл её дал — это заодно знаменатель для направления 5);
- [ ] шаблон PR с чек-листом «тест + мутация + CHANGELOG»;
- [ ] бейджи в README: лицензия, тесты (CI уже есть), «работает в Claude Code / Codex /
      Cursor / Gemini CLI» — соседи все перечисляют харнесы в первом экране;
- [ ] релизы GitHub по тегам с заметками из CHANGELOG (сейчас — только теги; заметки
      можно собирать release-drafter'ом или руками из раздела версии);
- [ ] `examples/` — готовый `docs/review/` на игрушечном репозитории: посетитель видит
      блоки, манифест, отчёт и реестр, не ставя ничего;
- [ ] дог-фудинг: `check` собственного репозитория в CI (соседи ревьюят себя своим
      инструментом на каждом PR — open-code-review, pr-agent, trailofbits);
- [ ] защита ветки `master`: PR и зелёный CI обязательны;
- [ ] описание и темы репозитория (`agent-skills`, `code-review`, `claude-code`, `codex`,
      `llm-agents`, `security-audit`), включённые Discussions для вопросов.

**Открытие и распространение:**

- [ ] `gh repo edit --visibility public`;
- [ ] `npx skills add mikey-semy/finetooth` заработает как есть; телеметрию skills.sh
      получают только публичные репозитории GitHub — после открытия набор попадёт в их
      каталог;
- [ ] заявка в каталоги скиллов (у сообщества их несколько; у Anthropic — `anthropics/skills`
      со своими правилами приёма), запись в awesome-списки;
- [ ] короткий скринкаст или GIF: `setup` → `coverage` → `prompt` → `check`;
- [ ] зеркало — необязательно: `git push --mirror` на второй адрес; разбор зеркалирования
      форджей есть в базе знаний первого проекта.

### Ревью PR — соседний класс, не наш

Дифф, а не инвентаризация; знаменателя покрытия нет; разделения ролей нет (кроме
«независимой рефлексии» у open-code-review).

- [The-PR-Agent/pr-agent](https://github.com/The-PR-Agent/pr-agent) — 13 125★, MIT: первый OSS
  PR-ревьюер; чек-лист соответствия как файл в репозитории проекта.
- [reviewdog](https://github.com/reviewdog/reviewdog) — 9 618★, MIT, не LLM: транспорт находок
  любого линтера в комментарии PR с `fail_level` — готовая форма ворот для узды.
- [danger-js](https://github.com/danger/danger-js) — 5 511★, MIT: правила ревью как код.
- [mattzcarey/shippie](https://github.com/mattzcarey/shippie) — 2 502★, MIT; [kodus-ai](https://github.com/kodustech/kodus-ai) —
  1 414★, AGPL-ядро, AST + LLM; [Nayjest/Gito](https://github.com/Nayjest/Gito) — 435★, MIT, умеет

## 4. Гигиена лучших: что есть у всех хороших

Сверены `alibaba/open-code-review`, `trailofbits/skills`, `obra/superpowers`, `OpenHack`,
`pr-agent` (плюс reviewdog и shannon).

У всех: `LICENSE`; README с установкой одной строкой в первом экране и списком харнесов;
`AGENTS.md`/`CLAUDE.md` в корне; шаблоны issue в yml с `config.yml`; CI, который проверяет
**сам формат скиллов** (у Trail of Bits — ещё и самотест валидатора, «чтобы проверка,
переставшая ловить, не зеленела вечно» — наш же принцип мутации); теги и релизы с
автосборкой заметок; **дог-фудинг** — репозиторий ревьюит собственные PR своим инструментом.

Ни у кого: `CITATION.cff`; бейдж тестов у скилл-репозиториев; CHANGELOG у скилл-репозиториев
(у Trail of Bits нет ни релизов, ни истории — у нас есть и то, и другое).

У finetooth уже есть: LICENSE, CHANGELOG, AGENTS.md, тесты, `skills-ref validate` в CI.
Не хватает — список в разделе 2.
