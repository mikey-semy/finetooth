# review-kit — сплошное ревью кодовой базы силами ИИ-агентов

Оснастка, которая превращает просьбу «проведи ревью проекта» в работу с доказуемым
результатом: код нарезан на блоки, каждый файл закреплён за блоком, состояние лежит на диске,
а не в переписке, и ищет дефекты один агент, чинит другой, проверяет правку третий.

Инструмент — один файл на стандартной библиотеке Python, без зависимостей.

## Зачем это нужно

Просьба «отревьюь проект» не работает по трём причинам, и каждая убивает результат по-своему.

**Контекст короче работы.** Ревью большого проекта — десятки часов и много сессий. Окно
кончается, история сжимается, и через два дня агент в новом окне начинает с нуля.
→ Здесь ни одна находка, ни один статус, ни одно решение не живут в диалоге: только в файлах.

**Нечем доказать полноту.** «Я посмотрел код» — утверждение, а не факт. Нельзя сказать,
прочитан ли файл, и особенно — есть ли файлы, которые не прочитал никто.
→ Здесь команда `coverage` пересобирает карту «файл → блок» и **падает**, если хоть один
отслеживаемый файл не принадлежит никому. Это и есть доказательство: не «мы посмотрели
важное», а «непокрытых файлов нет».

**Тот, кто ищет, не должен чинить.** Как только модель начинает править, она перестаёт
искать. А нашедший дефект — худший проверяющий своей же правки: он проверяет ту самую мысль,
которой ошибся.
→ Здесь три роли с отдельными промптами и правило: дифф починки читают агенты, которые его
не писали, **до** открытия предложения, а не после слияния.

## Откуда он взялся

Набор пришёл готовым: архив `review-kit.zip` от 16.09.2026, автор — разработчик проекта
**проект автора** (Go + два клиента на Next.js + сервис на Python, ~205 000 строк, GitLab).
Первый коммит этого репозитория — тот архив побайтно, без единой правки, чтобы дальше было
видно, что именно изменено и почему.

**Как он создавался — это главное, что в нём есть.** Набор не проектировали заранее. Его
вытащили из одного реально пройденного блока: автор прогнал ревью прав доступа на своём
проекте, по ходу шесть раз переписал инструмент и собрал получившееся в комплект. Поэтому
почти каждое правило в нём — след конкретной ошибки, а не общее соображение:

- **Пустой список путей означал «весь репозиторий».** Блоки, работающие на живом стенде,
  файлами не владеют — и покрытие сошлось на 100% с первого запуска, фиктивно. Теперь пустой
  список означает пустое множество.
- **Владение по каталогам отдавало чужое.** Редактор комментариев, лежащий в папке маршрута
  списков, достался бы блоку списков, и блок коммуникаций никогда бы его не открыл. Владение
  назначается по файлам, а «шаблон пути ничего не нашёл» — отдельная проверка: иначе блок
  молча сужается и агенту не отдают половину его кода.
- **Верификатор вписал в заголовок находки весь протокол проверки** на тысячу символов, и
  сводная таблица перестала быть таблицей. Появился предел в 220 символов и проверка на него.
- **Правка безопасности прошла все ворота и сломала работающее.** Линтер чист, тесты зелёные,
  миграции валидны — а мастер перестал видеть обходы своих техников. Причина универсальная:
  все новые тесты доказывали, что посторонний больше не видит лишнего, и ни один — что свой
  по-прежнему видит своё. Отсюда правило «тест пишется в обе стороны» и независимое ревью
  диффа до слияния.
- **Дыра нашлась в самой защите.** Шесть греп-ворот сборки запрещали опасные вызовы, а
  разрешающий комментарий рядом снимал запрет — и все шесть были написаны так, что комментарий
  освобождал **соседний** вызов: `grep -B 3` склеивает близкие совпадения в один блок.
  Движок, который сопоставляет находку с разрешением по номеру строки, лежит в
  `example/guard-grep.sh`.
- **Мёртвое право хуже отсутствующего.** Нашлась галочка «Закрытие заявок», существовавшая с
  первой миграции и не проверявшаяся нигде: администратор снимал её, чтобы запретить, и не
  происходило ничего.

Авторское описание целиком — [`docs/КАК-ЭТО-УСТРОЕНО.md`](docs/КАК-ЭТО-УСТРОЕНО.md). Числа в
нём — рассказ автора, мы их не проверяли; всё, что ниже помечено как проверенное, проверено
исполнением здесь.

## Что в наборе было сломано

Набор присылали как рабочий, и он рабочий — но установка по его же инструкции спотыкается.
Всё перечисленное воспроизведено на чистом репозитории, а не вычитано глазами.

| Что | Чем это оборачивается |
|---|---|
| `example/makefile-snippet.mk` содержит не цели ревью, а куски SAST-целей чужого проекта | **ни одна** команда `make review-*` из документации не существует; ставить приходится вслепую |
| документация зовёт `prompt BLOCK ROLE` | инструмент требует `prompt BLOCK --role`; команда из инструкции отвечает `unrecognized arguments` |
| `check` требует манифест у **всех** блоков сразу | манифест пишется перед своим блоком, значит проверка красная с первого дня — и её начинают игнорировать |
| блок закрывается с одним отчётом охотника | `set-status H1 closed` проходит без отчёта верификатора: непроверенные находки исчезают из остатка работ, проверка зелёная |
| устаревшая `coverage.tsv` не ловится | карта на диске расходится с пересчётом, и потребитель читает вчерашнее владение, не зная об этом |
| нет порога размера блока | блок, который физически не прочитать за сеанс, отчитывается об охвате, которого не было |
| нет команды перевести находку | README требует «правится только инструментом» и «проставьте `fixed` и коммит», а команды для этого нет — реестр правят руками |
| причина отказа ничем не потребована | условие завершения ревью требует причину у каждой отвергнутой находки, проверки на это нет, поле остаётся пустым |
| корень репозитория — «на два каталога выше файла» | инструмент, положенный не в `scripts/review/`, не падает, а молча ищет состояние в чужом месте и заводит второй комплект |
| отказ покрытия печатает только список путей | человек дописывает файл в первый попавшийся блок, и тот числится прочитанным, не будучи прочитанным |

Отдельно — грабли установки, не авторские, а наши, из другого языка и другой раскладки:

- **`[handle]` в git-pathspec — это класс символов.** Шаблон `src/app/[handle]/[slug]/edit/**`
  не совпадает ни с чем: глоб читает скобки как «один из символов h,a,n,d,l,e». Работает
  каталог без `**`. Проверка «шаблон ничего не нашёл» это ловит — без неё 46 файлов остались
  бы непокрытыми незаметно.
- **`exclusions` — список объектов** `{pattern, reason}`, не строк. Список строк роняет
  `coverage` с `TypeError`.

## Что исправлено в этой версии

Часть правок обкатана на живом ревью проекта проект В (67 блоков, 1691 файл, три блока
пройдены), часть добавлена здесь и проверена мутацией — сломать состояние и убедиться, что
проверка краснеет.

**Обкатано на живом ревью:**
- `check` требует отчёт **верификатора** у блока в статусе `verified`/`closed`;
- `check` сверяет `coverage.tsv` с пересчётом — устаревшая карта больше не молчит;
- манифест спрашивается только у блока, который дошёл до работы, а не у всех сразу;
- порог читаемости блока: 6000 строк, исключения при счёте **не** учитываются (иначе порог
  меряет `package-lock.json`, а не код, который агент будет читать);
- отказ покрытия говорит, что делать, и почему выбор делает человек, а не шаблон;
- отчёт охотника обязан содержать **поимённый список** прочитанных файлов: без него отчёт
  нельзя отличить от пересказа. У соседнего проекта именно это вскрыло приписку — 15 блоков
  из 26 числились проверенными, а 56 файлов не были названы ни разу.

**Добавлено здесь:**
- корень репозитория спрашивается у git — инструмент можно класть куда удобно;
- имя проекта и ворота стали подстановками `{{PROJECT}}` и `{{GATES}}` из `blocks.json`:
  скопированный без вычитки шаблон здоровался с агентом от имени чужого проекта;
- команда `set-finding <ID> <статус>` — переводит находку и не даёт поставить `fixed` без
  коммита, `rejected` без причины, `duplicate` без ссылки;
- `check` требует причину отказа у каждой отвергнутой находки;
- подсказки в сообщениях собраны в одну константу `CLI` (в исходнике половина звала `make`,
  половина `npm run` — оснастку переносили между проектами и не вычитали);
- `example/makefile-snippet.mk` содержит наконец цели ревью, а рядом лежит тот же список для
  `package.json`.

## Как поставить у себя

Проверено на чистом репозитории: команды ниже выполнялись ровно в этом порядке.

1. `review.py` — в `scripts/review/`, содержимое `prompts/` — в `docs/review/prompts/`,
   `example/точка-входа.md` — в `docs/review/README.md` и поправить под проект.
2. Написать `docs/review/invariants.md` — правила **своего** проекта. Самый важный файл: он
   вклеивается каждому агенту и решает, что тот сочтёт дефектом. В `example/` лежит чужой,
   смотреть ради структуры, а не содержания: там есть раздел «контекст, меняющий оценку
   находок» и раздел «что НЕ является находкой».
3. Расписать блоки в `docs/review/blocks.json` — сквозные сначала, доменные потом, стендовые
   последними (`example/blocks.example.json`). Заполнить `project` и `gates`.
4. Написать манифест первого блока: 10–15 гипотез **про свой проект** и критерий приёмки,
   который нельзя выполнить, не прочитав код. Самая долгая часть, и срезать её нельзя:
   манифест без проектных гипотез даёт ревью «по общим соображениям».
5. `init`, затем `coverage` — и разбираться с непокрытыми файлами, пока их не станет ноль.
   Здесь всплывает всё забытое: у автора — целый микросервис, у нас — 89 файлов маршрутов.
6. Добавить цели `make` (или скрипты `package.json`) и баннер в корневой файл инструкций
   проекта — без баннера новая сессия не узнает, что ревью идёт, и начнёт своё параллельное.
7. Прогнать первый блок целиком и **не бояться править оснастку по ходу**.

## Сколько это стоит

Замеры нашего ревью, три блока, по журналу:

| блок | что вышло | расход |
|---|---|---|
| доступ и видимость, 58 файлов / 4017 строк | 12 находок | 2 агента, 576 тыс. токенов, ~35 мин |
| доменное ядро, 13 файлов | 14 находок | 2 агента, 446 тыс. токенов, ~34 мин |
| запись и версии, 42 файла | 17 находок | 2 агента, 679 тыс. токенов, ~48 мин |

Блок, где чинить нечего, закрывается двумя агентами. Дорог не поиск, а круги починки: у
автора правка одного блока прошла три круга «починил → прочитали дифф» — 26 находок, потом
13, потом 8, потом четыре мелочи и вердикт «сливать можно». По нашей прикидке такой блок
стоит около двенадцати агентов против двух у обзорного. Сходимость и есть единственный
честный признак, что пора останавливаться, — правило остановки задаётся заранее и не по числу
находок, а по их роду.

## Чего не делать

- не начинать с доменных блоков: пока сквозные не задали язык, они дублируют друг друга;
- не давать одному агенту и искать, и чинить;
- не закрывать блок, у которого не выполнен критерий приёмки;
- не оставлять находки только в переписке;
- не держать больше двух-трёх агентов разом, если на этой же машине идёт сборка.

## Что внутри

```
review.py                         инструмент: init, status, coverage, prompt, import,
                                  set-status, set-finding, findings, check, log
prompts/hunter.md                 охотник: читает файлы блока и выдвигает находки
prompts/verify.md                 проверяющий: свой независимый проход, три вердикта
prompts/fix.md                    исполнитель: чинит, доказывает тестом, гоняет ворота
example/точка-входа.md            шаблон docs/review/README.md для проекта
example/blocks.example.json       три блока разных типов + исключения с обоснованием
example/manifest.example.md       манифест блока: гипотезы и критерий приёмки
example/invariants.example.md     чужие инварианты — как образец структуры
example/journal.example.md        шапка дневника решений
example/makefile-snippet.mk       цели make
example/package-json-snippet.json то же для проекта на npm
example/guard-grep.sh             движок греп-ворот: разрешение по номеру строки
example/баннер-в-корневые-инструкции.md
docs/КАК-ЭТО-УСТРОЕНО.md          описание автора набора, как есть
```

Статусы блока: `todo → running → hunted → verified → triaged → fixing → closed` (плюс
`blocked`). Статусы находки: `open`, `fixed`, `rejected`, `duplicate`, `deferred`.
