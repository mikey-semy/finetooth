# Полное ревью проекта проект автора — точка входа

**Если ты агент и только что открыл этот файл — прочитай его целиком, а потом
запусти `make review-status`. Больше ничего знать не нужно: всё состояние работы
лежит на диске, а не в чьём-то контексте.**

## Что это

Сплошное ревью всей кодовой базы (~205 000 строк) перед внедрением у заказчика.
Разбито на **29 блоков**, каждый размером в один сеанс чтения. Ревью идёт много
сессий подряд; контекстное окно короче, чем ревью, поэтому ни одно решение, ни
одна находка и ни один статус не живут в переписке — только в файлах этого
каталога.

## Устройство

| Файл | Что в нём |
|---|---|
| `blocks.json` | определение 29 блоков: пути, роль ревьюера, цель. Правится руками, редко |
| `state.json` | статус каждого блока. Правится только через `review.py set-status` |
| `findings.jsonl` | единый реестр находок, одна строка на находку |
| `findings.md` | человекочитаемый свод, **генерируется** из jsonl |
| `coverage.tsv` | карта «файл → блок», **генерируется**; доказательство полноты ревью |
| `invariants.md` | правила проекта; вклеиваются в промпт каждому агенту |
| `journal.md` | дневник решений: что решили и почему. Восстановлению не подлежит — пиши сразу |
| `blocks/*.md` | манифест блока: зачем, гипотезы, критерий приёмки |
| `prompts/*.md` | шаблоны промптов охотника, верификатора и исполнителя |
| `reports/*.md` | отчёты агентов. Пишет их сам агент, а не ведущая сессия |

## Порядок работы над одним блоком

```bash
make review-status                        # где мы и какой блок следующий
make review-prompt BLOCK=H1 ROLE=hunter   # полный промпт для агента-охотника
```

1. **Охотник.** Запусти агента промптом выше. Он читает все файлы блока, пишет
   `reports/<блок>.hunter.md` и черновик `reports/<блок>-findings.jsonl`.
   Переведи блок: `python3 scripts/review/review.py set-status H1 hunted`.
2. **Верификатор.** `make review-prompt BLOCK=H1 ROLE=verify`. Он проверяет
   каждую находку по текущему коду, отвергает ложные, добавляет свои и
   **перезаписывает** файл находок блока. Затем `set-status H1 verified`.
3. **Приёмка.** Прочитай оба отчёта сам. Сверь с критерием приёмки в манифесте.
   Если охват неполный — верни блок на повторный проход, а не закрывай.
4. **В реестр.** `make review-import BLOCK=H1 && make review-findings`.
5. **Дневник.** `python3 scripts/review/review.py log H1 "что решили и почему"`.
6. **Коммит.** Отдельным коммитом на ветку ревью. `git log -- docs/review`
   становится историей работы.
7. **Починка** идёт по правилам ниже.
8. **Ревью правок.** Дифф починки прочитывают независимые агенты, которые не
   чинили: бэкенд и фронтенд параллельно, дифф вклеен им в промпт целиком.
   Только после этого `set-status H1 closed`.

Два агента одного блока работают независимо и не читают выводы друг друга до
верификации. Больше двух-трёх агентов одновременно не запускать: на этой машине
живут раннеры CI, и во время конвейера процессор занят целиком.

## Правила починки

- **Чинит не тот, кто нашёл.** Ревьюер, начавший чинить, перестаёт искать.
  Промпт исполнителя: `make review-prompt BLOCK=H1 ROLE=fix`.
- **И проверяет не тот, кто чинил.** Правки — единственный код, который это
  ревью производит, и пишет его тот же ИИ, что и находил дефекты. Дифф уходит на
  независимое ревью до открытия MR, а не после слияния.
- **Как только находка подтверждена — в той же сессии**, не «запишем и вернёмся».
  Исключение: находка задевает ещё не отревьюенный блок — тогда после него.
- **Правки копятся на одной ветке и уезжают одним MR на партию** (примерно партия
  = фаза), чтобы не жечь конвейер на каждую строку. Критичное по безопасности —
  отдельным срочным MR, не дожидаясь партии.
- **Слияние только через merge request.** Ни `git merge` в `main`, ни прямого
  коммита, ни пуша в `main`. Пуш ветки MR не создаёт — создавай его опциями пуша
  и убеждайся, что GitLab ответил ссылкой на merge request.
- В реестре у находки проставляются `status: fixed` и коммит правки.
- **Никаких ссылок на ревью в коде**: идентификаторы находок, номера блоков и MR
  не должны попадать в комментарии и тесты — они умрут вместе с этим каталогом.

## Самопроверка

```bash
make review-check      # состояние непротиворечиво: статусы, отчёты, находки, покрытие
make review-coverage   # ни один файл репозитория не остался без блока
```

`review-check` ловит, в частности, блок, зависший в `running` больше суток, —
это почти всегда означает, что сессия оборвалась на середине и блок надо
перезапустить.

## Что считать завершением

Все блоки в статусе `closed`, в `findings.md` нет записей со статусом `open`, и
по каждой отвергнутой находке записана причина отказа.

## Как этот каталог умирает

Когда ревью закончено, **каталог `docs/review/` удаляется целиком одним MR**, а
долговечное из него переезжает туда, где живёт по-настоящему: правила — в
`CLAUDE.md`, архитектурные решения — в ADR, проверки — в тесты и ворота `make`.

Это не формальность. Проект уже обжигался на документах ревью, чьи таблицы
статусов никто не обновил: они описывали давно починенные дефекты как открытые и
вводили в заблуждение каждого, кто их открывал. Каталог ревью — это леса вокруг
стройки, а не часть здания.
